> 写代码前不要凭 SDK 的名字猜行为，拿不准就去服务器上读源码（路径见每条）。宿主源码根目录：`/opt/MaiBot`。

## 插件基本契约

- 必须在 `plugin.py` 模块级有 `create_plugin()`；`__init__.py` 只做 re-export。
- 插件类必须自己实现三个异步方法：`on_load()`、`on_unload()`、`on_config_update(scope, config_data, version)`，缺一个都加载失败（`src/plugin_runtime/runner/plugin_loader.py` 的 `_validate_sdk_plugin_contract`）。
- `_manifest.json` 逐字段校验，缺一个整包不注册：必须有 `i18n`、`plugin_type`；`display` 里只能有 `icon`。**用到的每个能力都要写进 `capabilities`**，否则运行时报 `E_CAPABILITY_DENIED`。
- 配置类继承 `PluginConfigBase`，`[plugin] enabled` 必须显式默认 `False`（宿主在没写时当成开启：`runner_main.py` 的 `_is_plugin_enabled`）。
- 运行时配置文件是 `plugins/<目录>/config.toml`；首次加载时宿主按默认值生成。改默认值时同时升 `config_version`。

### config.toml 文件监控（2026-10-28 读线上源码核实，`src/plugin_runtime/integration.py`）

- 宿主对**每个插件的 config.toml 有单独订阅**（`_refresh_plugin_config_watch_subscriptions`，按 plugin_id 订到具体文件路径）。文件变了 → `_handle_plugin_config_changes`：**只给这一个插件**发 `on_config_update(scope="self", config_data=规范化后的整份配置)`，**不会**让其他插件重载〔读源码〕。
  - 附带行为：文件里 `enabled` 从开着改成关 → 宿主会把这个插件**重载**掉（`reload_plugins_globally([plugin_id], reason="config_disabled")`）；关着的改成开 → 自动加载。MaiWork 网页改不到 `plugin.enabled`（不上网页），碰不到这条。
- 「源码变化 → 全部插件重载」的过滤器在 `_handle_plugin_source_changes`：**只有 `plugin.py`、`_manifest.json` 或任何 `.py` 后缀文件的变化**才算源码变化（`change.path.name in {"plugin.py", "_manifest.json"} or change.path.suffix == ".py"`）〔读源码〕。
  - 所以插件目录里 config.toml 之外**新建/改/删任何文件**都会触发全部插件热重载——MaiWork 网页写 config.toml 时**绝不在插件目录建临时文件**（config_file.py：内存里改好，`open(path,"w")` 直接覆盖写；备份写到数据目录 `<data_dir>/config-backups/`）。
  - config.toml 本身会被两个 watcher 同时看到：per-plugin config watcher（→ `on_config_update`）和 source watcher（不匹配 `.py` 过滤 → 无动作）。所以网页写 config.toml 只触发本插件的 `on_config_update`。
- 宿主给插件改配置的能力 `component.update_plugin_config` 只准内置插件管理用，MaiWork 用不了，所以网页写文件是插件自己写（config_file.py）。
- MaiWork **不给 MaiBot 的 planner 注册任何工具**（设计决定：MaiBot 端零工具）。

## 调能力的通用写法

```python
result = await self.ctx.call_capability("frequency.get_adjust", chat_id=session_id)
```

- 插件→宿主 RPC 默认超时 30 秒（`runner/rpc_client.py:176`），可以传 `timeout_ms=`。
- 返回值已经被 SDK 解包，**不要默认去查 `success`**：像 `config.get` 直接返回值、`chat.get_stream_by_group_id` 返回会话 dict。不在解包表里的能力返回完整信封（如 `send.text` 要自己判 `success`）。解包表在 `reference/maibot_sdk-2.8.1/maibot_sdk/context.py` 的 `_CAPABILITY_RESULT_KEYS`。统一在 `host.py` 里处理。

## 收消息：`chat.receive.after_process`〔实测〕

```python
@HookHandler("chat.receive.after_process", name="...", description="...",
             mode=HookMode.BLOCKING, timeout_ms=1500, error_policy=ErrorPolicy.SKIP)
async def on_msg(self, **kwargs): ...   # 返回 {"action": "continue"}
```

- 在消息入库、进入 MaiBot 聊天流程**之前**触发（`src/chat/message_receive/bot.py`）。
- `kwargs["message"]` 的键：`message_id`、`timestamp`、`platform`、`message_info`、`raw_message`、`is_at`、`is_mentioned`、`is_command`、`is_emoji`、`is_picture`、`is_notify`、`session_id`、`processed_plain_text`。群号在 `message_info.group_info.group_id`，发言人在 `message_info.user_info.user_id`。**没有 `text` 键**，文本用 `processed_plain_text`。
- 群里的表情回应等通知也会进来（`message_id` 形如 `notice:group_msg_emoji_like:...`），要过滤。
- 实测开销：普通消息处理 p50 0.0ms、最大 0.2ms；从 QQ 发出到进钩子 p50 0.85 秒。
- **不要对收到的消息返回 abort**：那会让消息不入库，MaiBot 的上下文和记忆就缺了这条。
- 钩子里不要做慢事（除了 mix 群 CHAT 下 @ 等 Jev 这一种，上限 1.5 秒）。
- 指令消息（如 `/work`）也会经过这里，且在 MaiBot 的指令处理之前。

## 让 MaiBot 闭嘴：两道闸〔实测〕

> v6 设计不再抢话筒，这一节**不再使用**，只作事实记录保留。

**第一道：频率 0。**
```python
await ctx.call_capability("frequency.get_adjust", chat_id=sid)        # 读原值（通常 1.0）
await ctx.call_capability("frequency.set_adjust", chat_id=sid, value=0.0)
```
- 效果：MaiBot 之后开新一轮思考时走「静默接收」——消息照常入库，不进 planner，不回复。
- **只改内存**，MaiBot 重启就丢；插件重载后要按库里记录重新设。
- 专注模式开启时有效频率被强制为 1.0（线上 `focus_mode = false`）。
- **实测漏洞**：@ 进来时如果 MaiBot 正在一轮思考中途，消息会被并进当前这一轮，照样回复。所以必须有第二道。

**第二道：发送闸 `send_service.before_send`。**
```python
@HookHandler("send_service.before_send", name="...", description="...",
             mode=HookMode.BLOCKING, timeout_ms=1000, error_policy=ErrorPolicy.SKIP)
async def before_send(self, **kwargs):
    msg = kwargs.get("message") or {}          # 序列化的待发消息，有 session_id、processed_plain_text
    if 该群闸开着 and 不是 MaiWork 自己的消息:
        return {"action": "abort"}
    return {"action": "continue"}
```
- 参数还有 `typing`、`set_reply`、`reply_message_id`、`storage_message`、`show_log`（`src/services/send_service.py`）。
- 实测：被拦的消息不发出、不入库，日志里是 `[SendService] 消息 ... 在发送前被 Hook 中止`。
- MaiWork 自己通过 `send.hybrid` 发的消息**也会经过这个钩子**，必须能认出来放行（设计：发送前登记「群 + 内容哈希」指纹，10 秒有效）。
- 闸开着时 MaiBot 对群里任何人的回复都会被拦，这正是 WORK 的效果；回 CHAT 必须立刻关闸。

## 给 MaiBot 同步任务进度：`maisaka.planner.before_request`

- 载荷有 7 个键：`items`、`item_schema_version`、`tool_definitions`、`selected_history_count`、`built_message_count`、`selection_reason`、`session_id`。**是 `items` 不是 `messages`**，读错字段会无声无效。
- item 形如 `{"item_type": "SystemMessageItem", "meta": {...}, "parts": [{"type": "text", "text": "..."}]}`。追加内容到第一个 system item 最后一个 text part，回写 `items`（保留 `item_schema_version`）。回写用 `modified_kwargs`，从 `dict(kwargs)` 复制后改，是整体替换。
- 不能取消 MaiBot 这一轮（`allow_abort=False`），默认超时 6 秒；解析失败宿主只打警告并忽略（`src/maisaka/chat_loop_service.py:1062-1092`）。
- 是否真的让 MaiBot 答得出进度，**还没实测**（M2 测）。

## 其他可用能力

- `knowledge.search(query, limit, mode, chat_id, person_id, group_id, time_start, time_end)`：查 MaiBot 长期记忆（A_Memorix），返回文本。插件**没有**写入记忆的正门。
- `config.get(key)`：如 `bot.qq_account`。
- `maisaka.proactive.trigger(stream_id, intent, reason, priority, metadata)`：请 MaiBot 在某个聊天流主动处理一轮。v6 用来冷场开话题、主动交代重要的事。**读过源码（2026-09-26），未实测**：
  - 实现：`src/plugin_runtime/capabilities/core.py:260` → `src/maisaka/runtime.py:661 enqueue_proactive_task`。
  - 做的事：往 MaiBot 的内存聊天上下文里追加一段文字「`<plugin_proactive_task id=... plugin_id=...>` 插件请求你主动处理一轮聊天：{intent} / 触发原因 / 优先级 / 附加信息(metadata 的 JSON) / 请结合当前聊天关系、记忆和上下文，自行决定是否回复以及如何表达。`</plugin_proactive_task>`」，然后立刻唤醒 MaiBot 跑一轮 planner（跳过它的等待状态，按「强制触发」处理）。
  - 这段文字**不写进消息库**，只在 MaiBot 内存上下文里；MaiBot 重启就没了。它会留在上下文里影响之后几轮。
  - **最终说不说由 MaiBot 自己决定**，可能不开口。MaiWork 要自己核对这之后 MaiBot 有没有真的发言（比如查消息库或挂 `send_service.after_send` 观察）。
  - 该群回复频率为 0 时，这一轮走「静默处理」，不会说话（`reasoning_engine.py:1211`）。普通的低频率（如 `talk_value = 0.3`）不挡。
  - 聊天流必须已存在（`chat_manager.get_existing_session_by_session_id`），否则返回 `success: False`。返回 `{"success": True, "stream_id", "task_id", "queued": True}`。
  - 开了专注模式的部署里，不在专注状态的聊天流可能会忽略已排队的触发（`reasoning_engine.py:1200` 附近），线上 `focus_mode = false`，暂不影响。
- `maisaka.context.append(stream_id, segments, visible_text, source_kind, message_id)`：往 MaiBot 上下文追加一条消息。目前不用，作为「可提起清单」的备选。
- `person.get_id(platform, user_id)` / `person.get_value(person_id, field_name)` / `person.get_id_by_name(name)`：读 MaiBot 的人物信息。**阶段 0 已查（2026-09-27，读源码 + 只读查库）**：
  - `get_value` 就是 `getattr(Person(person_id), field_name)`，没有白名单。字段：`is_known`、`person_id`、`person_name`、`name_reason`、`platform`、`user_id`、`nickname`（库列 user_nickname）、`group_cardname_list`、`memory_points`、`know_times`（库列 know_counts）、`know_since` / `last_know`（加载时没还原，**恒为 None**）。没认识的人只有 5 个属性，读别的字段会报错。
  - **没有任何字段反映「和 MaiBot 关系好不好」**：线上 371 人 `know_times` 全是 1、`memory_points` 全是空、没有好感度类字段。只有 `group_cardname_list`（群名片）有真实内容。
  - `person_id = md5(f"{platform}_{user_id}")`（platform 带 `-` 时取后半段），371 行全量核对一致，插件可以自己算。
  - 结论：关注成员里「和 MaiBot 关系好」改用 MaiWork 自己从消息里数的「和 MaiBot 的互动次数」（@ MaiBot、回复 MaiBot 的消息），不读 person 字段。（2026-09-27 用户新决定：互动计数数据保留在 `member_interactions`，但不再用来挑关注成员——候选改为近 30 天发言最多的前几位＋提过请求＋管理员加的。）
- MaiBot 的长期记忆 A_Memorix 自带**人物画像**（`[a_memorix.person_profile]` 已开，线上 213 人、1987 条快照）。**插件读不到**：画像入口 `memory_service.get_person_profile` 没注册成能力；`knowledge.search` 带 `person_id` 只做结果后置过滤，而且一条都没匹配时会退回全部结果（容易误以为过滤成功）。所以关注成员的个人画像由 MaiWork 自己记，`knowledge.search` 不传 `person_id`。

## 消息库里的图片、文件、引用（阶段 0 已查，2026-09-27）

- `mai_messages` 21 列，没有 url / 图片哈希 / 文件名列；这些只在 `raw_content`（msgpack）和 `processed_plain_text` 里。插件通过 `message.get_by_time_in_chat` 拿到的是同一批字段。
- **图片**：`processed_plain_text` 是 `[图片：描述]`，但描述是异步生成的，入库时还没生成就是**空字符串**（测试群 is_picture=1 的 22886 条里 8237 条文本为空），之后生成的描述只写进宿主的 `images` 表、不回写消息。表情包也标 `is_picture=1`（文本 `[表情包: …]`），`is_emoji` 列基本不用。→ MaiWork 读群时：图片空文本记作「[图片]」，不去追描述。
- **文件**：`processed_plain_text` 形如 `[文件] 名字，大小: 字节数，链接: https://…ftn_handler/…`（QQ 短时效链接）；`raw_content` 里另有 `file_id`。
- **引用回复**：`reply_to` 列 = 被回复消息的平台 `message_id`（可以直接对上）；约一半的回复在文本前面带 `[回复了某人的消息: 原文]`，另一半没有。所以判断「回复了 MaiBot」要看 `reply_to` 指向的消息是不是机器人发的，不能只看文本。
- `additional_config` 只有平台路由信息，没有媒体元数据。

## MaiBot 自己会不会主动找话题（读源码，2026-09-26）

- 没找到「群里冷场时自己开话题」的功能。MaiBot 说话都是被新消息、自己的等待超时、专注模式唤醒或插件主动任务触发的。
- `[experimental.attention_drift]`（注意力漂移，让回复更容易带出联想和小跑题）线上是关的，而且它只影响回复时的风格，不会在没人说话时开口。
- 结论：MaiWork 冷场开话题**不会和 MaiBot 自带功能撞车**。以后宿主升级要重新查一遍。
- `llm.generate_with_tools` 是单轮的，而且走宿主模型登记（30 秒 RPC 超时）；**MaiWork 用自己的 OpenAI 兼容客户端，不用它**。
- 宿主 WebUI 不能挂插件页面，控制台要自己起 aiohttp（先例：`plugins/neng_gong_zhi_ren`）。
- SDK 的 `EventType.ON_MESSAGE` 等事件在宿主里是被注释掉的，**挂了永远不触发**，别用。

## here.now 匿名发布（查官方文档 2026-09-27，**未实测**）

出处：`https://here.now/docs`、`https://here.now/openapi.json`、`https://here.now/llms.txt`、官方脚本 `heredotnow/skill` 的 `here-now/scripts/publish.sh`。不用任何账号 / API key。

1. `POST https://here.now/api/v1/publish`，不带 `Authorization`，JSON `{"files": [{"path": "index.html", "size": 1234, "contentType": "text/html; charset=utf-8", "hash": "<sha256 小写 hex>"}]}`（`path`、`size` 必填，路径是站内相对路径）。可带 `X-HereNow-Client: maiwork/plugin`（可选，建议带）。响应：`slug`、`siteUrl`、`upload.versionId`、`upload.uploads[]`（`path`、`method: PUT`、`url`、`headers`）、`upload.finalizeUrl`、`claimToken`、`claimUrl`、`expiresAt`。
2. 对每个 `upload.uploads[i]`：`PUT url`，只带它给的 `headers`（通常只有 `Content-Type`），**不带 Authorization**。目标域名是 `*.r2.cloudflarestorage.com`（服务器出网要能到这里）。预签名 1 小时有效。
3. `POST upload.finalizeUrl`，JSON `{"versionId": "..."}`，匿名不用鉴权；按 versionId 幂等（重试返回 `replayed: true`）；上传没到位返回 400 `missingFiles`。**finalize 成功前站点不算上线**；分享用返回的 `siteUrl` 原样。
- 限制：24 小时过期；每站 ≤2500 个文件；匿名单文件 ≤250MB；每 IP 每小时 60 次创建（429，带 `retry_after`）；匿名不能设密码、不能删（只能等过期）。
- `claimToken` / `claimUrl` 只返回一次，存进库里（claim 需要账号，MaiWork 不做；以后用户想保留可以把 claimUrl 给用户）。
- 错误统一 `{error, code, message, details?, retry_after?}`。

## Tavily MCP 端点（2026-09-27 实测）

第三方托管的 Tavily MCP 服务（Streamable HTTP 传输），作为 MaiWork `[search] provider = "tavily_mcp"` 的来源。地址形如 `https://<第三方主机>/mcp`（线上真实地址在插件 config.toml 里，不落仓库），鉴权头 `Authorization: Bearer <搜索密钥>`。在服务器上实测整链路约 1.3 秒。插件侧实现：`mcp_client.py`。

- 所有请求都是 `POST <端点>`，请求头带 `Content-Type: application/json` 和 `Accept: application/json, text/event-stream`；正文是 JSON-RPC 2.0。
- **第一步 initialize**：`{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"maiwork","version":"<插件版本>"}}}` → HTTP 200，`content-type: text/event-stream`，响应头带 `mcp-session-id: <会话ID>`，正文是 SSE：`event: message` + `data: {"id":1,"jsonrpc":"2.0","result":{...,"serverInfo":{"name":"tavily-mcp","version":"0.2.0"}}}`。
- **第二步 已初始化通知**：`{"jsonrpc":"2.0","method":"notifications/initialized"}`（无 id），请求头带 `Mcp-Session-Id: <上一步的会话ID>` → 202，空正文。
- **第三步 tools/call**：`{"jsonrpc":"2.0","id":N,"method":"tools/call","params":{"name":"tavily_search","arguments":{...}}}`（同样带 `Mcp-Session-Id`）→ SSE 里 `result.content[0].text` 是一个 **JSON 字符串**：`{"query": ..., "results": [{"url","title","content","score","raw_content","id"，可能有 "published_date"}], ...}`。
- `tavily_search` 实测用过的参数：`query`（字符串）、`max_results`（整数）、`topic`（`"general"` / `"news"`）、`time_range`（枚举 `"day" / "week" / "month" / "year"`，**不直接吃天数**，MaiWork 按 ≤1/≤7/≤31/其他 映射）。tools/list 里还有 `tavily_extract`（参数 urls）、`tavily_crawl`、`tavily_map`、`tavily_research`，MaiWork 本期只用 `tavily_search`。
- 工具业务失败：`result.isError == true`，`content[0].text` 是错误文字；协议失败走标准 JSON-RPC `error` 字段。
- 会话失效：对 initialize 以外的请求返回 HTTP 404（或 400 且错误文字提到 session）→ 重新 initialize 换新会话再发即可恢复；旧会话 ID 之后不可用。
- 响应可能是 SSE 也可能是纯 JSON（同一份 JSON-RPC 直接在响应体里），实现按响应体内容判型，不要只认 content-type。

## 上线实测（2026-09-27，第一次部署）

- **同一个群号可能有多条会话记录**：测试群 `900000001` 在 `chat_sessions` 里有两条——2025 年的旧记录（`account_id` 空、没有任何消息）和正在用的（`account_id` = 机器人 QQ，4.7 万条消息）。`chat.get_stream_by_group_id` 只返回第一条匹配（旧的），而且**忽略传入的 `account_id`**。MaiWork 改为用 `chat.get_group_streams` 列出全部群会话自己挑：优先 `account_id` 等于机器人 QQ 的，还分不出就看谁有最新消息。
- **新插件第一次放进 `plugins/`**：mv 后立刻 touch `_manifest.json` 不会触发加载（监控还没盯上新目录），要等几秒再 touch。
- **加载时是关着的插件，改 `config.toml` 打开不会激活它**（推断：宿主只给已激活的插件发配置更新）。要再 touch 一次 `_manifest.json` 让全部插件重载一次才会激活。以后首次部署可以直接把配置写好再放进去，只重载一次。
- 在宿主 venv 里跑契约测试会往 MaiBot 的 `logs/` 写一个新的日志文件（测试里起了一次 MaiWork）。无害，但看日志时别误会成线上加载。
- **`message.get_by_time_in_chat` 的 `limit` 默认取「区间里最新的 N 条」**（`limit_mode="latest"`，结果仍按时间正序；`src/common/message_repository.py` `find_messages`）。往后翻页必须传 `limit_mode="earliest"`，否则每页都拿到最新那一截、中间的全被跳过。第一次上线时 MaiWork 就这样只读到 2.6 小时（199 条），已修：首次回读一次取「7 天内最新 1500 条」，之后增量读用 earliest 翻页。测试里的假 MaiBot 也改成和线上一样的默认。
- **真模型的两个坑**（上线实测，本地假模型测不出）：① 群画像提示词只写了中文类别名，模型就回 `"category": "话题"`，代码只认英文代码 → 全被丢掉、群画像一直是空的。已改：提示词写明五个英文代码，代码也认常见中文叫法。② 子 agent 回填工具结果前没加 `assistant(tool_calls)` 那条消息，严格的端点（线上这个）直接 400，子 agent 一步都走不下去、资讯出不来。已改，并加了按 OpenAI 规范检查消息顺序的测试。
