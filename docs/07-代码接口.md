# 代码接口（模块之间的约定）

> 给写代码的人（和子 agent）看的：每个模块对外提供什么、不许做什么。设计理由看 `02-设计.md`，这里只写「怎么接」。
> 改了接口要同步改这里。M1 / M2 / M3 全部已落地；字段和签名以这里为准。
> 最后与代码核对：2026-09-27

## 0. 通用约定

- 包内一律相对导入（`from .store import Store`）。宿主用 `spec_from_file_location(..., submodule_search_locations=[插件目录])` 把插件目录当成包加载，相对导入可用（线上 `A_Mind` 插件就是这么写的）。
- 只依赖：标准库、`aiohttp`、`httpx`、`maibot_sdk`（宿主 venv 里都有）。**不要引入** aiosqlite、croniter、openpyxl 等宿主没有的库。
- 日志：`logging.getLogger("maiwork.<模块>")`。日志里不许出现密钥、请求头、完整模型请求。
- 时间：一律用 `clock.py`。存库用 epoch 秒（float），展示和「几点」判断用北京时间（固定 UTC+8，不用 zoneinfo）。
- 群号：内部统一用纯数字字符串（`"900000001"`）。配置里写 `"qq:900000001"`，由 `config.py` 解析。只支持 `qq` 平台。
- 注释、docstring、给用户看的文字用中文。
- 测试：`plugin/CharTyr_MaiWork/tests/`，pytest + pytest-asyncio（`asyncio_mode` 用标记 `@pytest.mark.asyncio`）。共用的假对象放 `tests/fakes.py`，路径设置放 `tests/conftest.py`。

## 4. store.py

```python
class Store:
    def __init__(self, path: Path): ...  # 目录不存在就建（0700），库文件 chmod 0600
    def migrate(self) -> int             # 幂等；返回当前版本（PRAGMA user_version）
    def close(self) -> None
    @contextmanager
    def tx(self) -> Iterator[sqlite3.Connection]   # 写事务：BEGIN IMMEDIATE … COMMIT / 出错 ROLLBACK；进程内一把锁 = 单写入者
    def read(self) -> sqlite3.Connection           # 只读查询用（同一连接，row_factory = sqlite3.Row）
    def event(self, conn, kind: str, *, group_id: str = "", entity: str = "", entity_id: str = "", payload: dict | None = None) -> int
        # 在调用方的事务里写一条事件（和状态更新同一事务）；payload 存 JSON，带 v=1
    def kv_get(self, key: str, default=None) -> Any      # JSON 值
    def kv_set(self, conn, key: str, value: Any) -> None
    def secret_get(self, name: str) -> str               # 没有返回 ""
    def secret_set(self, conn, name: str, value: str) -> None
    def prune(self, now: float) -> dict[str, int]        # 清理过期数据；返回各表删了多少条（见下）
def next_id(conn, prefix: str) -> str                    # 模块级函数：在调用方事务里取下一个编号，"T" -> "T-1"
```

- WAL、`synchronous=NORMAL`、`foreign_keys=ON`、`busy_timeout=5000`。
- 迁移是一个有序列表，每步一个函数；新阶段只能往后加，不改旧的。起步顺序：`_m1`（M1 表）→ `_m_profile`（群活跃统计补充）→ `_m2`（M2）→ `_m3`（M3）→ `_m_persona`（`focus_messages` 新表 + `focus_members` 加 `persona`/`persona_ts` 两列）→ …（`_m_quality` / `_m_humane` / `_m_personal` / `_m_group_space` / `_m_pending_asks` / `_m_model_calls`，看 store.py `_MIGRATIONS`）。
- `prune(now)`：`events` / `tool_calls` / `usage` / `judgments` 保留 30 天（`ts < now - 30*86400` 删掉），`mentions` 过期行物理删除；`model_calls` 留 3 天 / 最多 2000 行（哪个先到按哪个，models 每写 200 行也顺手清一次）；幂等，app 每天跑一次。
- 同步 API（库很小，调用在事件循环里直接执行；单次操作要短）。

M1 的表（字段以 `store.py` 为准，这里是要点）：

| 表 | 要点 |
|---|---|
| `kv(key PK, value JSON, updated)` | 模型设置（不含密钥）等杂项 |
| `secrets(name PK, value, updated)` | `model_api_key`、`console_secret`、`admin_password_hash`、`group_admin_pw.<群号>`（群管理员密码哈希，`sha256$salt$digest`，2026-10） |
| `events(id, ts, kind, group_id, entity, entity_id, payload, v)` | 事件流水 |
| `groups(group_id PK, workspace, session_id, name, member_count, token UNIQUE, created, last_msg_ts, cursor_ts, cursor_ids JSON, read_since, profile_ready_ts, last_refresh_ts, last_weekly_ts, fail_count)` + `_m_profile` 加的 `pending_count`（攒批计数）、`info_ts`（群信息最后更新时间） | 服务群的运行状态；`token` 是群链接码 |
| `profile_entries(id PK, group_id, category, text, evidence_count, evidence JSON, first_ts, last_ts, confidence, locked, deleted, source, updated)` | 群画像条目；`deleted=1` 是管理员墓碑（模型不许再加回来），`deleted=2` 是模型自己 remove 的（同文字照样能再加回，见 §8） |
| `bot_messages(group_id, message_id, ts, PK(group_id,message_id))` | `_m_profile` 新增：MaiBot 近 7 天发言 id（判断「回复了 MaiBot」用） |
| `member_interactions(group_id, user_id, day, count, PK(group_id,user_id,day))` | `_m_profile` 新增：每人每天 @ / 回复 MaiBot 次数（关注成员「和 MaiBot 聊得多」的依据） |
| `member_activity(group_id, user_id, day, count, name, PK(group_id,user_id,day))` | 每人每天发言数（关注成员、群人数估计） |
| `activity_bins(group_id, bin_ts, count, PK(group_id,bin_ts))` | 每 15 分钟发言数（群脉搏；M2 冷场判断用近几周同时段） |
| `focus_members(group_id, user_id, name, reasons JSON, note, pinned, removed, updated, persona, persona_ts, PK(group_id,user_id))` | 关注成员；`pinned`/`removed` 是管理员手动加 / 减；个人画像只在这里（`persona` 存 JSON `{summary,doing,cares,asked,style}`，`persona_ts` 最后刷新时间；`_m_persona` 加的列） |
| `focus_messages(group_id, user_id, ts, message_id, text, PK(group_id,message_id))` | `_m_persona` 新增：关注成员发言留存（个人画像素材，每人只留最近 14 天、最多 300 条；`text` 截 300 字）。只存当前关注成员（removed=0）且 personal_profile 开时的非机器人消息。只给管理员看；privacy 闸同名来源 |
| `usage(id, ts, day, role, model, purpose, group_id, task_id, prompt_tokens, completion_tokens, ok, ms, error)` | 模型用量 |
| `model_calls(id, ts, purpose, role, model, group_id, task_id, attempt, ok, status, ms, prompt_tokens, completion_tokens, error, request, response)` | `_m_model_calls`（0.3.9）新增的「最近模型请求日志」：chat() 每次尝试（成功/失败）写一行，attempt 从 1 起；status 是 HTTP 状态码（网络错误 0）；error 已遮密钥截 1000；request/response 是 JSON（messages 正文截 4000、整份 request 截 80KB、response.text 截 20000；**密钥绝不入库**，不存 headers）。管理员网页 `/api/logs/*` 读它（§9.4）；留 3 天 / 2000 行 |

画像类别（`category`）固定五个：`recent`（最近在聊）、`interest`（长期兴趣）、`ongoing`（在做的事）、`convention`（约定和说法）、`resource`（常用资源）。

## 6. intake.py（M1；M3 @ 识别和 /mw 指令）

```python
class Intake:
    def __init__(self, get_settings: Callable[[], Settings], signals: Signals, *,
                 jev=None, approvals=None, mentions=None, commands=None,
                 on_reminder: Callable[[str, dict], Any] | None = None,
                 bot_qq: Callable[[], str] | str | None = None,
                 spawn: Callable[[Awaitable], Any] | None = None, store=None,
                 on_answer: Callable[[str, str, str], Awaitable] | None = None,
                 waiting_tasks: Callable[[str], list] | None = None): ...
        # M3 注入的都可选：没注入对应能力就跳过（比如 approvals 空 → @ 走慢路径）
    async def handle(self, kwargs: dict) -> dict   # 钩子本体；async；任何异常吞掉，永远返回 {"action": "continue"}
    @property def slow_queue(self) -> list[dict]   # 只读视图：pending_asks 里 handled=0 的行（没接库的极简构造退回内存攒的）
class Signals:                           # 内存里的「有新消息」信号，给后台循环用
    def mark(self, group_id: str, session_id: str, ts: float) -> None
    def take(self) -> dict[str, Signal]  # 取走并清空：群号 -> Signal(session_id, last_ts, count)
    def last_ts(self, group_id: str) -> float
```

- 先判群：不是服务群立刻 `return continue`，**不读消息内容、不碰 store / host / models**。
- 过滤 `message_id` 以 `notice:` 开头的通知、`is_notify`。
- 机器人自己发的消息（`user_id == bot_qq`）：**只记信号**，不当请求、不问 Jev、不处理指令。
- 服务群的消息会记信号（`signals.mark`），然后走 M3 逻辑：机器人自己 → 只信号；`/mw` 开头 → 给 MaiBot 留一句备忘说明（2 分钟过期）+ 后台跑 `commands.handle`；被 @ → 钩子里只同步问 Jev（≤ timeout_ms），其余全部 spawn 成后台协程（详见 §11.5）。
- 提问的回答（docs/02 §7.2）：`waiting_tasks(群号)` 是 app 提供的内存缓存（「群 → [(task_id, question_msg_id, requester_id)]」，30 秒一刷、状态变化时主动失效），钩子里不做重查询。消息的 reply_to（raw_message 里的引用段）等于某任务的 question_msg_id，或发言人就是 requester_id 且这个群里他只有一个等待任务且消息 @ 了机器人 → spawn `on_answer(group_id, task_id, text)`（app 挂 `coordinator.resume`）。/mw 指令消息、机器人自己的消息不算回答；同一条消息只触发一次；提问那条消息的 QQ ID 由 outbox 发出 ask: 成功后回写到任务 `question_msg_id`（`Outbox.set_ask_hook`，app 的 `_on_ask_sent`）；resume 时记 task.answer 事件 + 时间线「收到回答：前 60 字」。
- 任何异常都吞掉并返回 continue（钩子永不中止消息）。

- **2026-10 起**：网页保存 = 直接写进插件 `config.toml` 的 `[models]`（含 api_key 明文，用户明确同意；写库覆盖层 `kv["models.settings"]` + `secrets["model_api_key"]` 已废弃，启动时一次性迁移进文件后删掉）。「测试连接」的可用模型列表/测试时间不是配置，存 `kv["models.checked"]`，端点一致时并进来显示。

- `transport` 参数用于测试注入 `httpx.MockTransport` 或指向本地假服务器。
- **端点级限流（2026-10 新增，治线上 429）**：按 `base_url` 规范化（去空格、小写、去末尾斜杠）分组，**不同端点互不影响**；状态只在进程内存，不落库，日志不打密钥。
  - **并发上限**：同一端点同一时刻最多 `max_concurrency` 个在途请求，超出的排队等（不报错）；冷却期间同端点的新请求和重试都先等到冷却结束再发。
  - **429 冷却**：任何一次 429 → 整个端点进冷却。有 `Retry-After`（秒数或 HTTP 日期）就用它、封顶 **120 秒**；没有就按连续 429 次数退避 **10 / 20 / 40 / 60 秒（封顶 60）**，再加 **±20% 抖动**。成功一次后连续 429 计数清零。进冷却时 info 日志一行（端点 host + 冷却秒数）。
  - **每分钟上限**：`max_rpm > 0` 时按端点做 60 秒滑动窗口，窗口内发出数到上限就等。
  - 两个设置：`[models] max_concurrency`（1~8，缺省 2）与 `[models] max_rpm`（0~600，缺省 0 = 关闭），config.py 越界夹回；`ModelSettings.public()` 带这两项，`Models.save()` 可改（没传保留当前值，非法给中文错），网页在「设置 → 模型 → 请求频率」。`[models] context_window`（8192~2000000，缺省 128000）同样进 `public()` / `save()`（没传保留），网页在「设置 → 模型 → 上下文长度」，「全部配置」里也能改。`POST /api/chat/{id}/compact` 摘要时模型出错 → 400「整理没成功：……」（不写半截摘要）。models.py 仍用 `getattr(settings.models, 名字, 缺省)` 读。
  - `list_models()`（测试连接）遇到端点还在冷却，直接抛 `ModelError("这个端点刚被限流（429），约 N 秒后再试")`，不干等。
  - 429 的重试等待交给端点冷却（不再用固定 `retry_delay_s`）；5xx / 网络错误的重试等待仍是 `retry_delay_s`，重试总次数不变。等待可取消（`CancelledError` 原样抛出）、不阻塞事件循环；限流用的时钟 / sleep 是模块级 `_NOW` / `_SLEEP`，测试可注入（`tests/test_model_throttle.py`）。
  - `list_models`（网页「测试连接」/ 列模型）不占并发名额、不算每分钟额度；冷却期内不等也不发，直接报错（见上）。

- 同一人的「每天最多 1 次」由 prepare_personal 自己的 mark_done 按北京日期判重；
  调度时间窗（9:00–22:00）只在 due 的挑人处判断（prepare 本身不判窗，手动跑不受限）。
- 个人向条目里的 `body / reason / basis` 出库前都过 `privacy.scrub`；mention 文本同样过。
  红线照旧：个人向内容（含 mention 文本里的画像暗示）绝不出现在群消息与群友可见文字里。

## 9. console（网页）

### 9.1 鉴权

- **管理员**：`POST /api/login {password}` → 设 cookie `mw_admin`（HttpOnly、SameSite=Strict、Path=/、7 天；值 = `<到期时间戳>.<HMAC>`，HMAC 密钥 = `secrets.console_secret`（没有就生成），签名内容混入当前密码指纹——改了管理员密码旧 cookie 立刻失效）。密码：`[console] password` 非空就用它；否则首次启动生成 16 位随机密码，`sha256$<salt>$<hash>` 存 `secrets.admin_password_hash`，明文写到 `<data_dir>/console_password.txt`（0600，目录 0700），日志只提示文件位置。同一 IP 10 分钟内错 5 次 → 429。实现见 `console/auth.py::ConsoleAuth`。
- **群管理员**（2026-10）：`POST /api/login {password}` 先按总管理员验；不对再用 `group_admins.py::GroupAdmins.match` 在**服务群**里找哪个群设了同样的密码，命中 → 同一个 cookie 名 `mw_admin`，值 = `g:<群号>.<到期时间戳>.<HMAC>`，签名内容 = `"group|<群号>|<到期>|<该群密码指纹>"`（指纹 = 密码哈希的 sha256 前 16 位；改了 / 清了这个群的密码，旧 cookie 立刻失效）。密码哈希 `secrets["group_admin_pw.<群号>"] = "sha256$<salt>$<digest>"`、名单 `kv["group_admins.<群号>"] = ["qq:123", ...]`（`config.norm_account` 规范化）——**只存数据库，不进 config.toml**；只总管理员能在网页上设（见下面 `group-admin` 三条）。群密码至少 8 位，和别的群 / 总管理员重复会拒；群不再是服务群 → 这个身份视为 none。登录失败限流和总管理员共用（同 IP）。实现见 `group_admins.py`。
- **群友**：请求头 `X-MW-Group: <群链接码>`。只能访问这个群的数据、只读（可反馈）。
- 所有非 GET 请求：有 `Origin` 头时必须和 `Host` 同源（host:port 归一后相等，http=80/https=443 补默认端口），否则 403。见 `console/auth.py::same_origin`。
- 管理员专属：设置、模型、用量、运行状态、请求日志、身份与工作记忆（全局）、扩展（MCP / skill / 搜索绑定）、来源屏蔽名单、和 MaiWork 聊、头像、群管理员自身的设置、其他群。群友请求这些一律 403（登录都没有的角色请求管理员接口是 401）；群管理员碰这些也是 403「群管理员只能管本群的事」。
- 按群的管理动作（群视图、群画像、关注成员、资讯偏好、现在就备一批、构想 do / dismiss、开话题记录标对错、RSS、本群工作记忆、重置本群链接、批准 / 拒绝本群派活、本群任务与目标操作、个人向内容的**读**）：总管理员随便，**本群**群管理员也能做；别的群一律 403。个人画像 / 个人向资讯的**写**（反馈、chat-vote、在群里提给他）群管理员 403「群管理员只能看，不能改个人画像」。
- 错误码约定（详见 §9.2 表下）：401 没登录、403 没权限 / 跨源、404 没找到、409 状态不允许、503 模块没开。

错误码约定（整个 console 一致；路由不存在也是 404「没有这个接口」，意外异常 500「服务器出错了」）：

- **401**：没登录、也没带有效群链接码（管理员接口回「先登录管理员」，通用接口回「先登录管理员，或用群链接打开」）。
- **403**：群友碰管理员专属、群友碰别的群、群友用群号访问 `/api/groups/{ref}`、跨源的非 GET 请求；群管理员碰全局的东西（403「群管理员只能管本群的事」）、碰别的群、碰个人画像 / 个人向资讯的写操作（403「群管理员只能看，不能改个人画像」）。
- **404**：群 / 条目 / 任务 / 请求 / 目标不存在；路由不存在。M2 写操作在调模块前先用 `_group_of` 查所属群，查不到即 404。
- **409**：状态不允许这次操作——批准 / 拒绝已非 pending 的请求、resume 非暂停任务、retry 非 failed 任务、goal 操作状态非法、`tasks.transition` 非法转移（`ValueError` → 409）。
- **503**：对应模块没开（feeds / topics / tasks / approvals / goals 为 None）→ `{"error": "这个功能还没开"}`。
- M2 idea 操作用 400 表示状态机非法（`idea_action` 抛 `ValueError`）；构想不存在是 404。

静态文件：`/` → `console/static/index.html`（no-cache）；`/static/...`；`/g/{token}` → 302 到 `/#/{token}/news`。响应头统一带 `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`。端口被占用网页不起来：记错误日志、不抛，插件其他功能照常。

### 9.5 用量历史（`GET /api/usage/history`；管理员）

参数二选一：

- `?days=N`：最近 N 天（含今天），默认 7，夹在 1..30；`N` 不是整数就用默认值；

  定 3–5 个**分散**的关注点（JSON；每项带 `source`：`recent` 最多 2 个、至少 1 个 `long`、再加 1 个
  `explore`；成功一次就把这批 query 追加进 `focus_hist`，最多留 15 个；只给 1 个也照常返回）→
  子 agent 拿「关注点 + 一段精简群画像（≤12 条，优先长期兴趣/在做的事，每条截 60 字）」用
  `web_search` / `fetch_page` 同时找
  「资讯」（最近几天）和「文章」（教程/好文章/工具介绍，不看新不新但要核对现在还适用；
  `[feeds] guides=false` 就只找资讯）。每条候选必须真打开过（`fetched: true` + `quote` ≤200 字原文依据）、

    打分模型顺带判的：grounded=false（「摘要在原文找不到依据」）、junk=true（「垃圾：原因」）、
    same_as_recent=true（「和最近出过的是同一件事（重复）」，打分 prompt 附最近 14 天已出标题作参考）。
  - 第二道·上网页：模型对每条打 info/source/relevance/timeliness/chat 五项 1–5 分
    （文章的 timeliness 是「现在还适用」，核对版本/价格/接口）、profile（群画像条目编号，
    代码换成文字；给不出 → relevance 封顶 2）、topic（≤8 字）、sensitive。
    avg=五项平均；avg ≥ `[feeds] web_min_avg`（默认 3）且 relevance ≥ 3 才上网页，
    否则 `rejected gate='web'`。再按 avg 高者留去同质化：同一 topic ≤2、同一域名 ≤3、
    敏感 ≤1、总数 ≤ `[feeds] max_items`（默认 10），落选 `gate='web'`
    （「同一个话题这轮已经留了两条」「超出本轮上限」「争议话题这轮已有一条」）。
  - 第三道·进话题候选池（`topics.add_candidate`）：kind=news、avg ≥ `[feeds] pool_min_avg`（默认 4）、

  主模型在最终入选的条目里挑最多 `[environments] verify_per_round`（默认 2）条 → 申请一台 railway.new 一次性 VM →

### 10.5 scheduler.py

```python
class Scheduler:
    def __init__(self, store, get_settings): ...
    def due(self, group_id: str, now: float, *, last_msg_ts: float = 0.0) -> list[str]
        # 这个时刻该做的事，返回 ["news", "idea", "goal"] 的子集（news 在前）
    def done(self, group_id: str, job: str, now: float) -> None
        # 记一笔做过；news 记在「实际时刻离 now 最近」的那个时段上；不认识的 job 只记警告日志
    def next_news_ts(self, group_id: str, now: float) -> float | None   # 下一个资讯时段的实际时刻（含固定偏移，最多往后看 3 天）
    def slot_ts(self, group_id: str, now: float, slot: str) -> float    # 某群、now 那天、某时段的实际时刻（时段 + 固定偏移）
```

- 资讯时段：`[feeds] news_slots` 每个时段加上按「群号 + 日期 + 时段」播种固定的随机偏移（`random.Random(f"{群号}:{日期}:{slot}")`，±`news_jitter_minutes`）；到点后 45 分钟内算数，**错过就不补**。
- 构想：每天一次，在 10:00–21:00 之间、群里安静时（距最后一条消息 ≥ 10 分钟；`last_msg_ts=0` 不知道就当安静）。
- 主动提目标（2026-10）：每天一次，在 19:00–21:00 之间、`[goals] propose` 开着（合并不配置后的有效值）才报 `"goal"`；跑不跑、提不提由 `GoalProposer` 决定。
- 睡觉时段（`[delivery] quiet_hours`）什么都不返回；群画像没成形（`groups.profile_ready_ts` 空 / 0，含库里没这个群）也什么都不返回。
- 状态存 kv：`sched.<群号>.news` = 已做过的 "日期|slot" 列表，按 done 时刻只留今天和昨天；`sched.<群号>.idea` / `sched.<群号>.goal` = 做过的日期（北京时间 YYYY-MM-DD）。
- app 的用法：每群每分钟 `due(...)` → 对 `"news"` spawn `feeds.prepare_news`、对 `"idea"` spawn `feeds.make_idea`、对 `"goal"` spawn `goal_proposal.GoalProposer.propose`（app 里的 kind 是 `"goal"`，跑不了就跳过）；长活结束（成功失败都算做过）就 `done(...)`，**错过不补**。整段只读 kv / groups，不碰模型、不发消息。

```python
    async def start(self, name: str, command: str, *, label: str, timeout_s: int) -> str
```

- 命令（systemd 模式）：`systemd-run --wait --collect --pipe --unit=maiwork-run-<随机> --uid=<run_as> --gid=<run_as> --setenv=PATH=… --setenv=HOME=<工作区> --setenv=LANG=C.UTF-8 -p MemoryMax=<m> -p MemorySwapMax=0 -p RuntimeMaxSec=<s> -p ProtectSystem=strict -p ProtectHome=read-only -p PrivateTmp=yes -p NoNewPrivileges=yes -p TemporaryFileSystem=<workspace_root> -p BindPaths=<本工作区> -p WorkingDirectory=<工作区> -- /bin/bash -lc <command>`（`03` / 线上实测过的写法；不带 `--quiet`，靠 stderr 末尾的 `Finished with result: oom-kill|timeout|exit-code` 判结果，超内存/超时时 systemd-run 退出码是 1 而不是 137）。显式的 `--setenv` 必给——不设的话单元里 HOME 是只读的 /home/maiwork。
- `[environments] local_mode = "systemd" | "direct"`：`direct` 只给本地测试用（直接跑子进程，不隔离），线上必须 `systemd`；`load_settings` 里 `local_mode` 写错、或**以 root 运行时配了 direct**（子 agent 会直接拿 root 权限）都强制回落 systemd 并记配置问题。
- direct 模式也只用最小环境（PATH / HOME=工作区 / LANG=C.UTF-8），绝不继承插件进程的环境（防密钥漏给子进程）；后台进程登记在实例内存表里，同名标签会先杀旧的再起。
- 输出各截 20000 字（留末尾）；oom 由 `Finished with result` 判定（direct 模式只能按退出码 137 / stderr 含 oom/memory 推断）；外层 asyncio.wait_for 在 RuntimeMaxSec 之上再加 15 秒兜底。
- 文件读写走 TOCTOU 三防线：父目录链逐段 lstat 拒绝符号链接、`os.open` 带 `O_NOFOLLOW` 末段链接拒开、打开后校验 fd 指向仍在工作区内（Linux 用 /proc/self/fd，其他平台 fstat 对 st_dev/st_ino）。写完（systemd 且 root）chown 给 run_as。

- 配额：官方同一出口 IP 每天最多 3 台、同时只有 1 台能用；MaiWork 再收紧到 `[environments] railway_daily_max`（默认 2，留 1 台给派活），同时只许 1 台——进程内锁 + `kv["railway.active"]` 标记，标记的 `expires_ts` 过了自动释放（顺带清本地 key 目录）。
- 怎么算「拿到了」：不带命令连一次（`ssh … railway.new < /dev/null`），JSON manifest 打在 stdout；`status` 是 `trial_starting` / `trial_ready` 且带 `build_expires_at` 才算拿到。`refused`（官方拿不到，退出码 13）一律当没拿到，原因换成人话写 `kv["railway.last_fail"]`（网页健康项显示「最近一次没拿到机器：…」）。
- `run` 之前看剩余时间：`build_expires_at - now < timeout_s + 120` 就拒（机器快到期，别放活），返回 `RunResult(exit_code=-1, timed_out=False)` 带中文说明。
- 释放语义：官方**没有**匿名 box 的销毁命令（实测 VM 里 pid 1 是 `/rwinit/init`），`release` = 本地删 `data_dir/railway/<job_id>/` + 清标记，然后等它 60 分钟到点被官方回收；key 一删这台机就永远找不回了。
- 安全：命令一律 `shlex.quote`、argv 传 exec（不过本机 shell）；ssh / scp / ssh-keygen 子进程只给最小环境（PATH / LANG / HOME），绝不继承插件进程的环境变量；manifest 的 `preview_url` / `human_claim_url` 只落成 Box 属性，不写日志、不外传（认领要账号，红线不做）。
- 工具侧：`vm_put_file` 只收**当前工作区里**的相对路径（绝对路径 / `..` / 符号链接逃逸一律拒），远端固定在 `/app/<字母数字._- 白名单文件名>`；`vm_read_file` 只读 `/app/` 下、回给模型截 20000 字；`vm_run` 的 `timeout_s` 夹到 ≤600 秒。没 box（拿不到机器 / 已释放）一律中文失败，不让模型瞎试。
- app 接线：`[environments] railway=true` 时 `_start_stack` 建 `RailwayEnv(self.get_settings, settings.data_dir, store=self.store)`，并 `register_vm_tools(self.tools, get_box=lambda: env.current_box, env=env)`（先注册 vm_run/put/read 这 3 个）；本机 `LocalEnv`（`self.env`）建好后第二遍再调一次 `register_vm_tools(..., local_env=self.env)`——`vm_run/put/read` 已在册被幂等跳过，只补出 `vm_fetch_file`。Feeds 的 `verify_runner` 是调 `feeds.run_railway_verify(items, picks, gid, settings, workers=…, tools=…, env=…)` 的闭包，railway=false 传 None。stop 时把手上的 box `release` 掉。Coordinator 从 `self.railway` 拿 RailwayEnv（`railway=None` 时不提供 railway 选项，app `_make_coordinator` 把 `railway=self.railway` 传进去）。
- 因为 app 启动时已经注册过 vm 工具，`run_railway_verify` 里那次注册会被幂等跳过——box 靠 `RailwayEnv.current_box` 现读（同时只许 1 台，谁占着就是它）。

### 11.6 群管理员（group_admins.py，2026-10 新增）

按群区分的管理员——网页上的第三种身份，只进数据库、不进 `config.toml`：

```python
class GroupAdmins:
    def __init__(self, store, *, get_settings=None, console_auth=None)
    def bind_console_auth(self, auth) -> None        # 总管理员密码比对（app/console 组装时接上）
    def served_gids(self) -> list[str]               # 服务群（拿不到配置就退回库里存过密码的群）
    def set_password(self, gid, password) -> None    # <8 位 / 和别的群或总管理员重复 → ValueError（中文）
    def clear_password(self, gid) -> None            # 幂等；该群旧 cookie 立刻失效
    def has_password(self, gid) -> bool
    def match(self, password) -> str | None          # 遍历服务群的哈希，命中返回群号；只认服务群
    def fingerprint(self, gid) -> str                # 密码哈希的短指纹（sha256 前 16 位）；没设密码 → ""
    def accounts(self, gid) -> list[str]             # kv["group_admins.<群号>"]，规范化成 ["qq:123", ...]
    def set_accounts(self, gid, accounts) -> list[str]   # 整份替换；认不出的账号 ValueError（中文）
    def is_group_admin(self, gid, user_id, platform="qq") -> bool
```

- 密码只进不出：网页接口和日志都不回显密码，指纹只用来签 cookie。
- 不同群不许用同一个密码，群管理员密码也不许和总管理员密码相同（登录时要能分清身份）；查重范围 = 服务群 + 库里残留过密码的群。
- 群不再是服务群 → `match` 不到、旧 cookie 视为 none。
- app 启动时建（`app.group_admins`），先接给 `Commands`（`/mw 批准` 按名单认本群管理员），ConsoleServer 组装时再接上 `ConsoleAuth`（双向：cookie 指纹 ← GroupAdmins，总管理员密码比对 → ConsoleAuth）。

## 13. 管理员对话（admin_chat.py、tools_admin.py；docs/02 §18；2026-09-27 新增）

- 注册表隔离：`Tools` 里 admin 角色单独一格（`tools.py::_admin_tools`）；`Tools.get(name, role)` 按角色取，角色不在这个工具的 roles 里就当没有；`tools.call()` 遇到另一格有同名工具，回「工具「X」只有主模型或子 agent 能用，当前角色不允许」（反向同理，文案换成「bot 管理员」）。注册 admin 工具时 roles 必须恰好 `{"admin"}`，混别的角色直接报错。
- 要确认的工具名固定一张表 `CONFIRM_TOOLS`：`send_group_message`、`group_notice_send`、`group_file_manage`、`group_album_upload`、`rss_remove`、`skill_delete`、`mcp_delete`、`profile_bulk_delete`、`approve_request`（群友派的活只能由管理员本人点头，模型不能代批）、`create_task`（任务开工后做完 / 做不成 / 缺信息时 coordinator 会自动往群里发消息，等于间接对外说话，所以要确认；小票摘要写「会派一个子 agent 去做：<标题>；做完 / 做不成时会在群 X 里说一句」）、`create_goal`（agent 目标后台检查时会往群里发汇报 / 完成话——coordinator 的 `goal:{id}:report` / `goal:{id}:done`——同理要确认；小票摘要写「会立一个后台目标：<标题>；之后会定期检查，有进展 / 完成时会在群 X 里说一句」）。`set_rules` 在 patch 碰到以下情况时才写小票（`_loosens_security`，值以当前有效设置为准比较；读不到当前值时沾边一律算放宽）：**approval 节任何字段**（`required` / `remind` / `admins` / `exempt_groups` / `exempt_users`，开关类打开也要确认）、`delivery.push_per_day` 变大（或 >5）、`delivery.quiet_hours` 安静窗口变窄、`topics.per_day` 变大 / `topics.min_gap_hours` 变小 / `topics.enabled` 从关到开。其余规则改动直接生效。
- 读资讯 / 任务详情的两个真接口坑（线上踩过）：`feeds.news_view(gid, days, admin=True)` 返回的是**批次**列表（每批 `{id, found, kept, skipped, note, rejected_count, items:[…], rejected:[…]}`），`list_news` 必须展开每批里的 `items` 读标题 / 链接 / 状态，并带上「被筛掉几条」；`tasks.detail_view` 的 dict 里**没有** `group_id` 键（`_list_item` 不带它），`task_detail` 做服务群检查要从 `Tasks.get(tid)` 的行上取 `group_id`。
- `refresh_profile`：工具优先调 `app.refresh_profile_now(gid)`（和 `run_news_now` 对称：非服务群 / 模型没配好 / 同群 `profile` 或 `profile_manual` 在跑 → `{"started": False, "reason"}`，否则 `_spawn_long_job(gid, "profile_manual", profiles.refresh(force=True))`）；svc 上没有这个方法时的回落也带同群互斥（svc 上的 `_mw_profile_now_running` 集合）。不对外发任何东西，不用确认。
- 取消任务真的停子 agent：统一入口 `app.cancel_task_run(tid)`——把登记在 `app._bg_jobs` 里名字为 `maiwork-task-<tid>` 的协程 `task.cancel()`，并从 `_running_tasks` 摘掉。所有取消路径都走它：网页 `op=cancel`（console/server.py `_stop_running_task`）、管理员工具 `cancel_task`（tools_admin）、`/mw 取消`（commands.py 的 `run_task_stopper`，app 接线时传 `self.cancel_task_run`）。兜底：coordinator `run_task` 每轮开头、`_run_one_attempt` 在子 agent 交回后，以及 workers `run` 每一步开头，都再查一次任务状态——已是 `cancelled`（或 `completed` / `failed` / `rejected`）立刻停，不再调模型、不再验收、不再交付、不往群里发任何东西。`Workers` 构造多了个可选 `tasks` 参数（app 传 `self.tasks`），给了才会做这一步查询。
- `set_rules` 的小票摘要是 `_patch_summary`：列出 patch 里**全部**字段（`节.字段 → 新值`，名单类显示成员，布尔显示开/关），超过 200 字截断并写明「共改 N 项」。
- 小票参数 = 执行凭据：带群的确认类工具在写票前把解析出的群号（可能是对话焦点群）补进 `args["group_id"]`；`PendingGate.execute` 直接用票里的 args 构造 `ToolContext(group_id=...)`，不依赖当时的对话焦点。
- 参数防伪造 + 指纹式批准：工具层包装器把 `_` 开头的参数一律剥掉再执行（`_norm_args`）；「管理员已同意」由 `_APPROVED_CTX`（ContextVar）承载，值是 `_fingerprint(tool, args) = (工具名, sha256(规范化参数 json.dumps(sort_keys=True, ensure_ascii=False)))`，只有 `PendingGate.execute(approve=True)` 在执行那一下置上；`_need_confirm` 只在当前 (工具, 规范化参数) 与指纹完全一致时放行——execute 期间 handler 派出的子任务继承了 ContextVar 也对不上别的 (工具, 参数)，照样写新票。
- `PendingGate.execute` 用 `asyncio.wait_for(handler, tool.timeout_s)` 限时（`timeout_s<=0` 按 60 秒）：超时标 `failed` 并回「执行「X」超时（N 秒没跑完），这次动作已作废」。
- 相册路径限制：`group_album_upload`（管理员版和 `tools_groupspace` 主模型版 alike）写票 / 执行前先过 `_check_upload_path(path, workspace_root / workspace_of(gid))`——拒符号链接（lstat），`resolve()` 后必须在该群工作区目录下；不合规直接中文拒绝，不写票、不调群空间。
- `make_idea_now`：工具优先调 `app.make_idea_now(gid)`（和 `run_news_now` 对称：非服务群 / 模型没配好 / 同群 `idea` 或 `idea_manual` 在跑 → `{"started": False, "reason"}`，否则 `_spawn_long_job(gid, "idea_manual", feeds.make_idea)`）；svc 上没有这个方法时的回落也带同群互斥（svc 上的 `_mw_idea_now_running` 集合），重复点回「这个群已经在想构想了，等它想完」。定时巡检 `_schedule_round` 到点的 `idea` 在 `idea_manual` 还在跑时跳过这一轮。
- `reject_request` 也过 `_served()`（请求所在群不是服务群 → 中文拒绝，不动）；`list_requests` 不带群号（或填 `*`）时只列服务群（`WHERE group_id IN 服务群`），`read_logs` 只给服务群和全局（`group_id=''`）的调用记录。
- 小票必须有归属对话：`PendingGate._ensure_chat` 只返回 `bind_chat` 绑定过的 chat_id；没绑定（ContextVar 和实例回落都是 0）时 `queue` 直接回「管理员对话还没绑定，这个动作先记不下小票：请在网页对话里重发一次」，不建对话、不写票。

### 13.2 网页接口

只管理员（群友 403「这里只有管理员能进」、没登录 401「先登录管理员」）；`svc.admin_chat` 为 None 一律 503「这个功能还没开」。所有响应出网页前过一遍 `_redact_json` 密钥遮罩。

| 方法 路径 | 请求体 | 返回 | 错误 |
|---|---|---|---|
| `GET /api/chat` | 无 | `{"chats": [Chat 每项多一个 running]}` | 401 / 403 / 503 |
| `POST /api/chat` | `{"group_id"?: "群号或链接码"}`（不传 / 空 = 不聚焦；链接码用 `_resolve_ref` 换成群号） | 单个 `Chat` | 400 请求体不是 JSON；404 群不是服务群 |
| `PATCH /api/chat/{id}` | 至少给一个：`{"title"?, "group_id"?, "archived"?}`（archived 必须是 true / false；group_id 空串 = 不聚焦） | 单个 `Chat` | 400 id 不是数字 / 标题空 / archived 不是布尔 / 没有要改的字段 / 值不合规（标题太长等）；404 对话不存在或群不是服务群；409 这段对话在忙 |

- `POST /api/chat/{id}/messages` 立刻返回（消息先落库，模型在后台答）；前端用 `GET /api/chat/{id}?after=<最后一条消息 id>` 轮询拿增量，`running=true` 时禁发送、显示「正在回答」。
- 忙（`ChatBusy`）按**类名**认，server.py 不 import admin_chat 模块；`PATCH` 的 409 分支照抄同一套判定（`update` 本身不会抛忙，属兜底）。
- 错误分岔：对话在、只是值不合规 → 400；对话不在 → 404。`POST /api/chat/pending/{pid}` 的「已经处理过」走 409（`confirm` 抛 `PendingDecided`，ValueError 子类，同样按类名认）；网页收到 409 会重新拉一遍对话，把过期的确认卡片收掉。
- 标题：新对话默认「群名｜管理员对话」；第一句话发出时若标题还是默认的，就改成这句话（压成一行、最多 24 字）；手动改过的标题不动。
